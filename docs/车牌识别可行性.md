# 车牌识别可行性评估

> 结论先行：**当前视频源无法识别车牌，这不是实现问题，是成像阶段的物理限制。**
> 本文记录实测数据与推导过程，供后续接入高分辨率卡口相机时对照。

## 1. 实测数据

探测脚本：`backend/scripts/probe_plate_pixels.py`
测量对象：河南高速云视频真实直播流

| 项目 | 实测值 |
|---|---|
| 上游分辨率 | **352 × 288** |
| 编码 / 帧率 | H.264 / 25 fps |
| 分片大小 | 约 37~41 KB（每片 2 秒 50 帧） |
| 画面中车辆检测框 | **14.8 × 16.1 px**（高速远距离） |
| 画面中车辆检测框 | **114.9 px 宽**（画面内最近的车辆） |
| 反推车牌尺寸 | **3.6 × 1.1 px** |
| **车牌字符高度** | **0.8 px**（远车） / **6.1 px**（近车） |
| OCR 可读下限 | 约 **16 px** |

**差距约 2.6~20 倍。** 车牌字符高度不足 1 个像素时，信息在成像阶段就已经丢失，
任何超分辨率或识别算法都无法恢复。

## 2. 推导过程

车牌尺寸的估算是纯几何换算，不涉及任何模型，因此结论是确定性的：

```
中国民用号牌           440 × 140 mm        （宽高比 3.14:1）
车牌宽 / 车宽          约 24%              （1.8 m 车宽、0.44 m 牌宽）
号牌字符高 / 牌高      约 70%              （上下留白）

车辆框宽 114.9 px
  → 车牌宽 = 114.9 × 0.24 = 27.6 px
  → 车牌高 = 27.6 / 3.14  = 8.8 px
  → 字符高 = 8.8 × 0.70   = 6.1 px      ← 远低于 16 px 的下限
```

## 3. 部署要求的反推

要让车牌字符高度达到 16 px，反推所需的车辆框尺寸：

```
字符高 16 px
  → 牌高 = 16 / 0.70      = 22.9 px
  → 牌宽 = 22.9 × 3.14    = 71.8 px
  → 车宽 = 71.8 / 0.24    = 299 px
```

**即：车辆在画面中必须至少占 299 像素宽。**

| 分辨率 | 车辆需占画面宽 | 含义 |
|---|---|---|
| 352 × 288（当前） | 85% | 不可能，整幅画面只有 352 px |
| 1280 × 720 | **23.4%** | 约每 4 辆车里只有 1 辆能读 |
| 1920 × 1080 | 15.6% | 近景卡口场景可行 |

**关键认识：接入 720p 相机并不自动等于"能读牌"**，还要保证车牌在画面中足够大。
这通常意味着：

- 相机安装在**近景卡口位置**（车辆必须减速通过、且距离近）
- 或使用**长焦镜头**压缩视野

高速公路**主线监控**的远景视角，即使换成 4K 也读不出牌——因为车辆在画面里
依然只占很小的比例。这是视角问题，不是分辨率问题。

## 4. 代码中的处理

### 4.1 分辨率预检（`plate_recognizer.py`）

系统在调用任何识别引擎**之前**先做几何预检：

```python
def estimate_plate_char_height(bbox, frame_width, frame_height) -> float:
    box_width_px = bbox.w * frame_width
    plate_width_px = box_width_px * PLATE_TO_VEHICLE_WIDTH   # 0.24
    plate_height_px = plate_width_px / PLATE_ASPECT          # 3.14
    return plate_height_px * PLATE_CHAR_HEIGHT_RATIO         # 0.7
```

低于 `MIN_READABLE_CHAR_HEIGHT = 16` 时**直接返回「不可读」并附上估算依据**，
不调用引擎。这样做有两个好处：

1. **可解释**。用户看到的是「这个框只有 6.1 px/字符，读不出来」，
   而不是一个莫名其妙的空结果。
2. **防错**。在公安业务里，一个**错误的车牌号意味着查错人**。
   预检会拦住所有本来就读不出的车辆，避免把识别噪声当成车牌号送进车主查询。

### 4.2 三个通道（`plate_recognizer.py`）

| 通道 | key | 默认 | 说明 |
|---|---|---|---|
| 未接入 | `none` | ✅ | 如实报告不可用，不返回任何数据 |
| 模拟 | `mock` | | 生成确定性假车牌，**带 `simulated` 标记**，仅用于演示 |
| 正式 | `official` | | 占位，需接入卡口相机或第三方服务 |

**为什么默认不是 `mock`**：模拟数据格式正确，若被误接入业务流程，
可能触发对无辜车主的查询。仿真数据必须**显式启用**，且界面必须显示标记。

### 4.3 接入方式

1. 部署高分辨率卡口相机（车辆占画面宽 ≥ 23%）
2. 在 `plate_recognizer.py` 的 `OfficialPlateRecognizer._do_recognize`
   中实现具体调用（本地模型或第三方服务）
3. 配置 `SURVEILLANCE_PLATE_ENGINE=official`

预检逻辑**无需改动** —— 它会在新分辨率下自动放行可读的车辆，
继续拦截远处读不出的那些。

## 5. 对系统整体的影响

车牌识别不可用**不影响**违停检测主流程：

- 违停判定只依赖轨迹位移与时间，**不需要**车牌
- 告警记录中 `plate` 为空、`plateMessage` 说明原因，前端据此展示
- 车主查询接口独立存在，可在**人工识别车牌后**手动查询

也就是说，完整的业务闭环是：

```
持续巡检 → 违停告警（无需车牌） → 人工查看快照核验
                                      ↓
                              如能看清车牌则手动输入
                                      ↓
                              车主查询（脱敏 + 留痕）
```

接入卡口相机后，中间的人工环节可以自动化，**其余部分无需改动**。

## 6. 复现方式

```bash
cd backend
.venv\Scripts\python.exe scripts\probe_plate_pixels.py [摄像头编号]
```

脚本会抓取真实画面，输出每个车辆框的尺寸、反推的车牌像素与可读性判定，
并给出与部署要求的对比结论。

## 附录：为什么不是"换个更大的模型"就能解决

本项目在检测环节已经做过类似的优化（见 `docs/模型选型实验.md`）：
把推理尺寸从 640 提到 960，在小目标召回上有明显收益。但**那条经验不适用于车牌**。

区别在于：

- **目标检测**是在**已知区域**内判断"这里有没有车"。把 352×288 放大到 960×960
  能让特征图上的目标尺寸更接近训练分布，因此有效。
- **字符识别**需要读取**笔画级**的信息。车牌字符高度 0.8 px 意味着整个字符
  只覆盖不到 1 个像素——放大 3 倍后是 2.4 px，仍然是糊的。**放大不产生信息**。

这是信息论层面的限制，不是模型能力问题。
